# openCloud v0.4.1

> La v0.4.0 a été taguée mais **jamais publiée** (build en échec, test instable, #390) : la v0.4.1 reprend son contenu et corrige les tests.

Depuis la [v0.3.0](https://github.com/ldesfontaine/opencloud/releases/tag/v0.3.0).
Les numéros `#…` sont ceux des tickets Forgejo.

## En bref

- Les **sauvegardes se voient** : un inventaire de ce qui existe à sauvegarder et de ce que Proxmox garde déjà, et l'historique des exécutions de chaque plan.
- Un **jeton d'API en écriture se limite** à des machines et à des invités Proxmox précis.
- Un **arrêt demandé** (`docker stop`, `restart`, Compose) qui sort en code non nul n'est plus pris pour un plantage.
- Le reste est de la documentation : cadrage de la refonte UX, étude restic, ligne directrice des modules.

## À faire en mettant à jour

1. **Sauvegarder la base** avant de remplacer le binaire : `avant-maj.db` ([Mettre à jour](../installation.md#mettre-à-jour)).
2. **Le serveur d'abord.** Les migrations `019` à `023` s'appliquent seules au démarrage de `serve`, dans l'ordre, chacune dans sa transaction. Rien à lancer.

   | Migration | Ajoute |
   | --- | --- |
   | `019` | `backup_runs` : l'historique des exécutions des plans |
   | `020` | les archives vzdump observées par invité Proxmox |
   | `021` | `machine_volumes` : les volumes Docker rapportés |
   | `022` | `containers.stop_requested` et `container_events.stop_requested` (défaut 0) |
   | `023` | la portée des jetons : `api_tokens.machines_limited` et `guests_limited`, `api_token_machines`, `api_token_guests` |

3. **Puis les agents.**
   - Ceux des machines qui portent Docker : tant qu'ils sont anciens, l'inventaire n'y voit aucun volume.
   - Tous, pour le correctif #385 : un agent ancien ne rapporte pas `stop_requested`, et le code de sortie décide seul comme avant.
   - Le protocole de l'agent est inchangé (2) : un agent ancien reste connecté.
4. **Configuration (`config.toml`) : aucun changement requis.**
5. L'inventaire des archives Proxmox se remplit au prochain relevé de chaque hôte (toutes les 5 minutes).

## Ce qui change / casse

Vérifié par la comparaison de `v0.3.0` (`origin/main`) à `dev` : **aucune route retirée ni renommée**, **aucun champ JSON retiré ou renommé**, **aucune clé d'erreur retirée**. Il n'y a que des ajouts.

| Quoi | Avant | Maintenant |
| --- | --- | --- |
| Routes (`routes.txt`) | — | + `GET /api/backups/inventory`, + `GET /api/backups/runs`, + `PUT /api/settings/api-tokens/{id}/reach` |
| `GET /api/settings/api-tokens` | par jeton : `verbs` | + `machines` et `guests` par jeton (`null` = sans limite) ; + `machines` (les machines à cocher) |
| `GET /api/token/verbs` | verbes | + `reach` |
| Conteneurs (`container`, `containers`, `machine_containers`, `network`, `transitions`) | — | + `stop_requested` (booléen) sur la fiche et sur chaque transition |
| `last_targets_ok`, `last_targets_failed` d'un plan | en mémoire, perdus au redémarrage | lus dans l'historique ; un plan qui n'a pas encore repassé garde 0 et 0 |
| Pastille d'un conteneur sorti en code non nul après un arrêt demandé | « Défaillant » | « Arrêté » |
| Alerte « service arrêté sans qu'on l'ait demandé » | Un code hors 0, 137 et 143 la déclenche | Ne se déclenche plus si l'arrêt était demandé (`oom` et `killed` inchangés) |
| Jeton d'API sur une route de sauvegardes | `403` partout | Lecture permise sur `/api/backups/inventory` et `/api/backups/runs` seulement ; `/api/backups` reste `403` |
| Geste d'un jeton limité qui vise une autre machine ou un autre invité | — | `403 api_token.out_of_scope` |

**Ce qu'un client MCP voit.**
- Un jeton `read` existant marche comme avant, et lit en plus l'inventaire et l'historique des sauvegardes.
- `GET /api/token/verbs` rend `reach` : un client qui le lit sait avant d'agir où son jeton porte. Un client qui ne le lit pas reçoit `403 api_token.out_of_scope` et peut s'en tenir à ce message.
- Les golden JSON ne changent que par ces ajouts de champs ; un client qui ignore les champs inconnus n'est pas touché.
- Ce côté client (mcp-maison) n'a pas été vérifié ici.

**Pas de retour arrière du binaire du serveur** : la base est en migration `023`, une v0.3.0 refuse de démarrer dessus. Pour revenir : l'ancien binaire **et** la copie `avant-maj.db`.

## Sécurité

| Quoi | Garantie | Limite |
| --- | --- | --- |
| Portée d'un jeton | Un geste qui vise une autre machine ou un autre invité est refusé (`403 api_token.out_of_scope`) et journalisé avec le jeton, la machine et l'invité visés | Elle ne limite que les **gestes** : les lectures restent sans portée, un jeton limité à une machine lit encore les autres |
| Jetons existants | La migration `023` les laisse sur « toutes les machines » : rien ne change pour eux | Réduire leur portée est un geste de l'opérateur, rien n'est limité à sa place |
| Modifier une portée | Opérateur seulement : un jeton ne peut pas élargir la sienne | — |
| Machine supprimée | Elle sort de la liste sans que la liste s'élargisse : un jeton limité à une machine qui disparaît n'agit plus sur rien | — |
| Invités Proxmox | Un numéro d'invité est jugé en plus de la machine hôte | Un numéro vaut sur chaque hôte Proxmox admis : deux hôtes qui portent le même numéro ne se distinguent pas |
| Tâche sans machine | — | Elle n'est dans aucune liste : un jeton limité aux machines ne peut pas la mettre en pause |
| Inventaire et historique | Lecture seule, aucun secret ; rien n'est écrit sur les machines | Les noms de machines, d'invités et de volumes sont lisibles par tout jeton `read` |

## Ce que ça ne fait pas

- Rien n'est sauvegardé de plus : aucun producteur ne prend encore un volume Docker.
- Une destination d'openCloud et un stockage Proxmox qui sont le même endroit physique restent deux lignes : ils ne sont pas rapprochés.
- Une archive vzdump dont le numéro ne correspond à aucun invité du dernier relevé n'est rattachée à rien.
