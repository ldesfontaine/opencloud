# openCloud v0.3.0

Depuis la [v0.2.0](https://github.com/ldesfontaine/opencloud/releases/tag/v0.2.0).
Les numéros `#…` sont ceux des pull requests Forgejo.

## En bref

- Un agent IA peut **agir**, pas seulement lire : jetons d'API en écriture, avec une liste de verbes réversibles cochés par l'opérateur.
- Proxmox : l'agent reconnaît l'hôte, et peut démarrer, arrêter proprement et photographier une VM. Nouveau module Pare-feu (OPNsense, lecture seule).
- Une mise à jour d'agent qui ne tient pas se **défait seule** en trois minutes. En échange, **chaque agent doit recevoir une fois le lanceur stable** (root) : sans lui, openCloud n'envoie plus de mise à jour.
- Le journal d'audit nomme l'acteur : personne, jeton, agent ou règle.

## À faire en mettant à jour

1. **Sauvegarder la base** avant de remplacer le binaire ([Mettre à jour](../installation.md#mettre-à-jour)).
2. **Migrations `014` à `018` : rien à lancer.** Elles s'appliquent seules au démarrage de `serve`, dans l'ordre, chacune dans sa transaction (`internal/store/store.go`). La `013` (Proxmox) était déjà dans la v0.2.0.

   | Migration | Ajoute |
   | --- | --- |
   | `014` | `machine_roles` : les rôles que l'agent reconnaît |
   | `015` | les tables du Pare-feu (secret d'API scellé) |
   | `016` | `api_token_verbs` : les verbes de chaque jeton |
   | `017` | `audit_events.actor_label` ; le déclencheur « ajout seul » du journal est recréé |
   | `018` | `agents.rollback_version`, `machines.update_last` |

3. **Le lanceur stable, une fois par agent, par root.** `agent.update` et `agent.rollback` ne sont permis qu'aux agents qui tournent sous le lanceur `opencloud guard` (copie du binaire posée par root hors de `bin/`, que l'unité systemd lance). Sans lui : `409 action.rollback_unavailable`, la fiche dit « Cette machine doit être migrée avant d'être mise à jour ». **Cela vaut aussi pour l'agent de la machine openCloud.**
   - Procédure et lignes à jouer : [Migrer l'agent vers le retour arrière automatique](../installation.md#migrer-lagent-vers-le-retour-arrière-automatique) (l'interface les produit aussi, `GET /api/agent-migration`). Elle pose en même temps le binaire de cette version : l'agent redémarre sur la v0.3.0.
   - Une installation neuve suit déjà l'unité de `docs/installation/opencloud-agent.service` (`ExecStart` = le lanceur).
   - Un agent non migré **continue de fonctionner** et d'observer ; il ne peut simplement plus être mis à jour depuis l'interface (ni par un jeton).
   - Après la migration : `journalctl -u opencloud-agent -n 20` dit `agent starting` puis `connected`, et la fiche affiche « Retour arrière automatique : Oui ».
4. **Configuration (`config.toml`) : aucun changement requis.** Aucune option nouvelle ni retirée.
5. **Droits d'agent : rien n'est coché à votre place.**
   - `proxmox.power` et `proxmox.snapshot` ne se proposent qu'à une machine où le rôle `proxmox_ve` est vu ; pour les utiliser, cochez-les (fiche › Agent › **Changer les droits**) et posez le jeton Proxmox local selon les commandes que la page affiche.
   - Le droit `agent.update` existant est celui qu'exigent aussi `agent.rollback` et le lanceur.
6. **Pare-feu** : déclarer un pare-feu est facultatif ; il demande un utilisateur d'API OPNsense en lecture.
7. **mcp-maison** : un jeton `read` existant marche comme avant. Les verbes d'un jeton `write` ne servent que si le client lit `GET /api/token/verbs` ; ce côté n'a pas été vérifié ici.

## Changements qui cassent

Vérifié par la comparaison de `v0.2.0` à `dev` : **aucune route retirée ni renommée** (`routes.txt` n'a que des ajouts), **aucun champ JSON retiré ou renommé** (les gabarits n'ont que des ajouts : `verbs`, `update_last`, `roles`, `rollback_capable`, `actor_label`, `own_snapshots`), **aucune clé d'erreur retirée**, protocole de l'agent inchangé (2). Ce qui change en revanche de comportement :

| Quoi | Avant | Maintenant |
| --- | --- | --- |
| Mettre à jour un agent non migré | Permis | `409 action.rollback_unavailable` ; migrer d'abord (ci-dessus) |
| Deux mises à jour d'agent en même temps | Permises | `409 action.update_in_progress` jusqu'à confirmation, échec ou 30 minutes |
| Créer un jeton d'API au nom d'un jeton vivant | Permis | `409 api_token.name_taken` (deux jetons du même nom ne se distinguent plus à l'audit) ; les jetons existants ne sont pas renommés |
| `scope: "write"` à la création d'un jeton | `422 api_token.scope_invalid` | Accepté ; `verbs` est refusé sur un jeton `read` (`422 api_token.verbs_need_write`), un verbe inconnu aussi (`422 api_token.verb_unknown`) |
| Jeton d'API sur une route d'écriture | `403 api_token.route_forbidden` | Idem, sauf le verbe que le jeton porte ; un verbe non porté : `403 api_token.verb_forbidden` |
| Unité de l'agent (installation neuve) | `ExecStart=…/bin/current agent …` | `ExecStart=…/opencloud-guard guard -state … agent -state …` ; une unité existante n'est pas touchée |
| Libellés du journal | « Opérateur », « Commande » | « Personne », « CLI » (interface seulement) |
| `opencloud secrets forget` | Efface les secrets Proxmox | Efface aussi ceux des pare-feu (sortie : une ligne de plus) |

**Pas de retour arrière du binaire du serveur** : la base est en migration `018`, une v0.2.0 refuse de démarrer dessus. Pour revenir : l'ancien binaire **et** la copie faite avant la mise à jour.

## Sécurité

| Quoi | Garantie | Limite |
| --- | --- | --- |
| Garde `proxmox.self_target` | Un arrêt de la VM qui héberge openCloud est refusé (`409`), par l'interface comme par un jeton | Elle repose sur le rapprochement par nom d'hôte avec la machine `local` : une VM dont le nom d'hôte diffère n'est pas reconnue |
| Débit par jeton | Dix verbes d'un coup, puis un toutes les deux secondes ; au-delà `429` avec `Retry-After`. Compté après le droit | Distinct des échecs d'authentification, qui restent limités par adresse |
| `on_behalf_of` | Lu seulement de l'en-tête `X-MCP-Maison-User` d'une requête admise par jeton, exactement une valeur, sans caractère de contrôle, 200 caractères ; posé par le journal après le nettoyage, **jamais lu du corps** (un test y met une valeur forgée) | Indicatif, pas une preuve : il n'ouvre aucun droit |
| Verbe non porté | Refusé, journalisé (`api_token.deny`), trace limitée à cinq d'un coup puis une par minute | Le refus lui-même n'est jamais limité |
| Liste blanche | Un jeton n'ouvre que ses lectures et ses verbes ; une route ajoutée plus tard lui est fermée | Un jeton `write` peut, selon ses verbes, éteindre proprement une VM ou redémarrer l'agent d'une machine : cela se défait et se lit à l'audit, mais coupe le service entre-temps |
| Jeton Proxmox d'écriture | Il reste **sur l'hôte**, au compte de l'agent (`0600`) ; le serveur n'en a jamais, et ne le voit jamais | Le rôle Proxmox limite aux privilèges `VM.PowerMgmt` et `VM.Snapshot`, pas aux gestes : un agent compromis peut couper de force ou supprimer n'importe quel instantané. L'empreinte du certificat est obligatoire |
| Mise à jour d'agent | L'agent revérifie la signature avec sa propre clé ; aucun verbe ne signe ni n'importe de version | Le lanceur est une copie figée qu'il faut reposer à la main s'il change |
| Pare-feu | Secret d'API scellé en base, jamais rendu ; masqué pour un jeton | `opencloud secrets forget` l'efface ; à ressaisir |

Les commandes `pveum` de la page du jeton Proxmox n'ont pas été éprouvées sur un vrai Proxmox (voir `docs/projet/22-fonctionnement.md`).
